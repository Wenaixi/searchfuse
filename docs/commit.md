# Git 提交规范

## 提交信息格式

```
<类型>[可选范围]: <祈使句摘要>

[可选正文]

[可选脚注]
```

- 摘要用祈使句，不超过 72 个字符
- 结尾不加句号
- 只在能增加清晰度时使用范围（例如 `auth`、`api`、`ui`）
- 破坏性变更用 `!` 标记（例如 `feat!:`），或写一行 `BREAKING CHANGE:` 脚注

## 可用类型

| 类型 | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 文档更新 |
| `style` | 格式调整（不改逻辑） |
| `refactor` | 代码重构（不改行为） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `build` | 构建系统或依赖变更 |
| `ci` | CI/CD 变更 |
| `chore` | 杂务 |
| `revert` | 回退一次提交 |

## 原子提交原则

1. 一次提交只做一件事
2. 每次提交之后仓库都应当仍可构建、仍可运行
3. 每次提交都应当能被独立回退，只影响它对应的那一处改动
4. 行为有变化时，把相关测试放在同一次提交里
5. 不要把重构、格式化与行为变更混在一次提交里

## 提交流程

```bash
# 1. 查看改动
git status --short
git diff --staged --stat

# 2. 选择性暂存（避免 git add -A）
git add <具体文件>

# 3. 复核将要提交的内容
git diff --staged

# 4. 提交（HEREDOC 格式，正文里说清「为什么」而不是「改了什么」）
git commit -F- <<'EOF'
<类型>[范围]: <摘要>

<正文：问题是什么、为什么这样改、验证过什么>
EOF
```

不要加 `Co-Authored-By` 之类的署名尾巴：这个仓库的提交历史里没有，作者的署名由 git 配置决定。

## 注意事项

- 不要提交 `.env`、凭据之类敏感文件
- 提交钩子失败后，修好问题再建一次**新提交**（不要用 `--amend`）
- 不要自动推送；等用户的指示
